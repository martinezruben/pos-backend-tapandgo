## Plan: operar todo el backend en GMT−4 (America/Santo_Domingo)

**Decisión de contrato API (importante):** los timestamps que viajan al POS seguirán en **UTC ISO con sufijo Z** (`2026-09-04T02:00:00Z`). Es un instante inequívoco que la app ya sabe convertir; cambiarlo a hora local rompería la app y ~15 formatos sin beneficio. "Que el API funcione en GMT−4" se logra porque **el servidor interpreta hoy/ayer, ventanas de días, filtros y reportes en hora local** y las conversiones de ida y vuelta con el POS son exactas (ISO Z ↔ epoch).

### 1. Configuración
- `.env` y `.env.example`: `APP_TIMEZONE=America/Santo_Domingo` (reemplaza `America/La_Paz`, misma zona GMT−4 pero nombre canónico con soporte de tz).
- `deploy.sh`: el `.env` generado pasa a `America/Santo_Domingo`.
- `config/app.php`: se mantiene `pos_sales_timezone` (ReportController ya lo usa) alineado al mismo valor por defecto.

### 2. Soporte `App\Support\LocalDate` (nuevo)
- `sqlDate(string $column): string` — expresión SQL que convierte la fecha almacenada (UTC) a fecha local antes de agrupar:
  - MySQL: `DATE(CONVERT_TZ(col,'+00:00','-04:00'))` (offset fijo calculado de `config('app.timezone')` — Santo_Domingo no tiene DST, es estable).
  - sqlite: `date(col,'-4 hours')` (modificador con offset calculado).
- `whereLocalDate(Builder $q, string $column, string $operator, string $date)` — compara usando la expresión anterior (reemplaza `whereDate` crudo).

### 3. Corregir los agrupamientos/filtros que usaban fecha UTC
- **DashboardController**: `whereDate('occurred_at', $today)` de ventas/tickets de hoy → `LocalDate::whereLocalDate`; `dailySalesTrend()` y `syncSuccessFailedByDay()` agrupan con `LocalDate::sqlDate()` en vez de `DATE()`/`strftime` crudo (hoy una venta a las 22:00 local caía en el día UTC siguiente).
- **AdminGridQuery** (filtros `date_from`/`date_to` de los grids, ej. reporte de transacciones): `whereDate` → `LocalDate::whereLocalDate`.

### 4. Tests en GMT−4
- `phpunit.xml`: `APP_TIMEZONE=America/Santo_Domingo`.
- `tests/TestCase.php`: `date_default_timezone_set('America/Santo_Domingo')` + `config(['app.timezone' => ...])` (hoy fuerza UTC; GMT−4 no tiene DST, así que las aserciones son estables todo el año).
- Ajustar tests que asuman UTC si los hay; los payloads del API siguen siendo ISO Z explícito, así que no deberían cambiar.
- **Tests nuevos**: venta a las 23:00 local (03:00 UTC del día siguiente) cuenta en el día local correcto en dashboard y en el filtro de fecha del grid de transacciones.
